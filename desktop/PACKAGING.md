# Shipping open-emulator

```bash
cd desktop
npm install
npm run dist:win     # -> release/open-emulator-Setup-<version>.exe  (~75 MB)
```

`dist:win` builds the app, regenerates the icon, and runs electron-builder. `dist:dir` does the
same without producing an installer, which is faster when you only want to poke at
`release/win-unpacked/`.

## What the installer does

One click, per user, no UAC prompt, launches when it finishes — the flow LDPlayer and BlueStacks
use. Nothing large lands in the install directory, so there is no reason to make anyone choose a
drive: the Android images live inside WSL.

## The backend ships outside the asar

`extraResources` copies `android/`, `scripts/`, and `Makefile` to `resources/backend/`, and
`repoRootWinPath()` (`src/main/win-paths.ts`) looks there first.

This is not optional. The app copies that tree into the WSL distro on first run, and an asar is a
single file — a path inside it is not a real directory, so `tar` and `cp` cannot read it. Packaged
without this, every install would look fine and fail the moment it tried to reach its own backend.

The generated trees are excluded from the copy (`sdk`, `avd`, `state`, `logs`, `*.img`, `*.qcow2`):
they belong to the distro, not to the installer, and shipping them would add gigabytes to a file
whose useful payload is about 100 KB.

## What a user still has to download

The installer is ~75 MB. On first run the app then needs WSL2 plus roughly 4 GB of Android system
image, which the setup screen fetches by itself. **Say this on the download page.** It is not a
"download and run" app, and finding that out after double-clicking is a bad first impression.

## Code signing

The installer is unsigned, so Windows SmartScreen shows *"Windows protected your PC"* and the user
has to click through **More info → Run anyway**. There is no way around this except a certificate:

- A standard OV certificate (~$200–400/yr) works immediately but builds SmartScreen reputation
  slowly — early downloaders still see the warning.
- An EV certificate costs more and carries reputation from the first signature.

With a certificate, set `CSC_LINK` (path or base64 of the `.pfx`) and `CSC_KEY_PASSWORD` in the
environment; electron-builder picks them up with no config change.

## Icon

`build/icon.png` is generated by `scripts/make-icon.mjs` rather than checked in — the repo carries
the recipe instead of an opaque binary. `npm run icon` regenerates it; `dist:win` does so
automatically.

## Version and releases

The installer takes its version from `package.json`. Bump it before a release: installed copies
only update to a version higher than their own.

Releases are published by `.github/workflows/release.yml` when a `v<version>` tag is pushed. It
tests, builds on Windows, and uploads the installer, its `.blockmap` and `latest.yml` — the file
installed copies read to find updates. `npm run release:win` is the same build with publishing on;
it needs `GH_TOKEN`. The full procedure, and how the in-app updater behaves, is in
[documentation.md](../documentation.md#publishing-a-release).

## Known local snag

electron-builder unpacks a code-signing toolchain into
`%LOCALAPPDATA%\electron-builder\Cache\winCodeSign`, and that archive contains two macOS symlinks.
Windows refuses to create symlinks without Developer Mode or elevation, so the extraction fails with
*"A required privilege is not held by the client"* — even though a Windows build never uses those
files.

Either enable Developer Mode, or pre-extract the archive without them once:

```powershell
$cache = "$env:LOCALAPPDATA\electron-builder\Cache\winCodeSign"
& .\node_modules\7zip-bin\win\x64\7za.exe x -bd -y "$cache\winCodeSign-2.6.0.7z" `
    "-o$cache\winCodeSign-2.6.0" "-xr!darwin"
```

electron-builder finds the populated directory and skips the download.
